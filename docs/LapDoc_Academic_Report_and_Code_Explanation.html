1. Executive Summary & Abstract

LapDoc is a classical Knowledge-Based Expert System (KBES) developed for component-level fault isolation, electrical safety verification, and subsystem health scoring in portable personal computers. Developed within the classical symbolic artificial intelligence paradigm formulated by Feigenbaum, Buchanan, and Shortliffe, LapDoc solves a critical engineering problem: providing rapid, non-invasive, deterministic, and verifiable fault triage without requiring destructive disassembly or physical test probes in early diagnostic stages.

A frequent skepticism encountered during academic project defenses is the "Wizard Fallacy": Is the system truly an Artificial Intelligence system, or merely an elaborate sequence of hardcoded if/elif/else branches?

Core Academic Thesis
LapDoc is an authentic Knowledge-Based Expert System. It strictly decouples declarative domain knowledge (stored in knowledge_base.json) from the domain-independent procedural inference engine (implemented in engine.py). Swapping the knowledge file transforms the engine into a medical, automotive, or industrial triage system without altering a single line of Python execution code.

LapDoc incorporates bidirectional explanation facilities (answering both WHY a question is being asked and HOW a conclusion was reached), certainty factor mathematics derived from Stanford's MYCIN project, explicit domain boundary detection, and a multi-subsystem audit scorecard.

3. Procedural Script vs. True Symbolic Expert System

During academic evaluation, examiners frequently interrogate the distinction between a script and an expert system. The epistemological differences are profound:

Dimension Procedural Script / Decision Wizard LapDoc Symbolic Expert System
Knowledge Locality Embedded in procedural code (if/else statements in application files). Completely decoupled. Zero hardware facts reside in engine.py; all reside in knowledge_base.json.
Reasoning Flexibility Single rigid tree path. Cannot support alternative traversal modes. Dual reasoning engines: Rapid Emergency Early-Exit DAG + Cascading Gateway Subsystem Audit.
Explanation Capability None or hardcoded console strings. Cannot explain its internal state. Dynamic introspection. Can explain why a query matters and trace derivations backwards.
Maintenance Overhead Altering a rule requires editing Python source, creating regression risks. Domain experts edit JSON schema without touching engine or UI code.
Handling Uncertainty Binary logic (True/False only). Fails when symptoms are ambiguous. Shortliffe Certainty Factors ($0.0 \le CF \le 1.0$), competing hypotheses, and differential rankings.
Domain Awareness Blind execution. Halts with uncaught exceptions or outputs erroneous leaves. Explicit boundary definitions, threshold gating ($CF < 0.60$), and out-of-scope intercepts.

  4. Memory & Storage Subsystem (SO-DIMM RAM training, NVMe/SATA controller, SMART telemetry)
  5. Motherboard & Core Logic Subsystem (EC/KBC controller, BIOS/UEFI SPI ROM, RTC CMOS, power rails)
  6. Input/Output & Peripherals (USB host controller, keyboard matrix, precision trackpad, audio codec)
  7. Structural & Physical Integrity (hinge anchors, liquid spill detection, chassis grounding)

5. The Inference Engine Architecture (engine.py)

The inference engine implements two complementary reasoning paradigms:

  1. Forward-Chaining Early-Exit DAG (Emergency Mode): Traverses candidate rules from root symptom assertion (q_emergency_triage) towards terminal leaves. If a choice contains a leaf_diagnosis, the engine immediately terminates traversal and derives the diagnosis, pruning irrelevant questions.
  2. Cascading Gateway Subsystem Pipeline (Comprehensive Mode): Iterates systematically across each of the 7 hardware subsystems. Each subsystem begins with a Gateway Node. If the gateway is asserted healthy, the entire subsystem branch is pruned ($O(1)$ fast path). If anomalous, the engine branches deeper into clinical verification nodes.

6. Inexact Reasoning & Certainty Factor Calculus

In hardware fault diagnostics, human observation is frequently incomplete or ambiguous. LapDoc avoids naive binary assumptions by adopting the Shortliffe & Buchanan (1975) Certainty Factor ($CF$) model formulated for Stanford's MYCIN project.

Certainty Factor Representation

Every rule assertion yields a Certainty Factor $CF \in [0.0, 1.0]$:

  • $CF = 1.0$ (Deterministic Certainty): Physical, unambiguous empirical proof (e.g., fractured DC jack pin, visibly swollen Li-ion pouch cell).
  • $0.60 \le CF < 1.0$ (Strong Hypothesis): Highly correlated symptom requiring secondary confirmation (e.g., faint screen under flashlight indicates backlight failure with $CF = 0.95$).
  • $CF < 0.60$ (Inconclusive Differential State): Ambiguous symptoms compatible with multiple root causes (e.g., black screen with spinning fan).

Independent Evidence Combination Formula

When two independent pieces of corroborating evidence support the same fault hypothesis, their certainty values are combined using the monotonic MYCIN operator:

$$CF_{combined}(CF_1, CF_2) = CF_1 + CF_2 \cdot (1.0 - CF_1) \quad ext{where } CF_1, CF_2 \ge 0$$

In engine.py, this is implemented as an atomic static method: 

@staticmethod
def combine_certainties(cf1: float, cf2: float) -> float:
    """
    MYCIN standard certainty combination for positive independent evidence:
    CF_combined = CF1 + CF2 * (1 - CF1)
    Clamped strictly to [0.0, 1.0].
    """
    cf1 = max(0.0, min(1.0, float(cf1)))
    cf2 = max(0.0, min(1.0, float(cf2)))
    return round(cf1 + cf2 * (1.0 - cf1), 4)

Mathematical Property: The combination function is commutative ($CF(a,b) = CF(b,a)$), associative ($CF(a, CF(b,c)) = CF(CF(a,b), c)$), and asymptotically approaches $1.0$ without ever exceeding certainty boundaries.

7. Explanation Facility & Working Memory ("Why" & "How")

A cornerstone of Knowledge Engineering is that an expert system must explain its reasoning to human operators. LapDoc satisfies both classical Buchanan-Shortliffe explanation criteria:

1. Dynamic Justification: Answering "WHY"

Before answering any diagnostic question, the technician or user may inspect the system's motive. LapDoc retrieves the declarative why property of the active node: 

def explain_question(self, node_id: str) -> str:
    node = self.get_node(node_id)
    if not node:
        return "Node not found in knowledge base."
    return node.get("why", "Diagnosing system state based on observed symptoms.")

Example: When asking "Does the laptop power on when removing the main battery and running solely on the AC adapter?", explain_question() outputs: "Isolates a shorted battery management system (BMS) or dead cell from a faulty AC charging adapter or blown motherboard DC-in MOSFET."

2. Chronological Deduction Audit: Answering "HOW"

Upon reaching a terminal diagnosis, LapDoc reconstructs the complete chain of working memory assertions. The resulting history_trace lists every question evaluated, the user's specific observation, the rule triggered, and the clinical test protocol executed.

8. Limitation Awareness: "Knowing What It Knows"

In his seminal treatise "Knowledge Engineering for the 1980s", Edward Feigenbaum stated that the defining boundary between brittle scripts and true expert systems is that an expert system must know its own limitations. LapDoc enforces this principle through three architectural guarantees:

Domain Boundary Contract
In-Scope: Non-invasive electrical, firmware, thermal, and component-level diagnostic triage for portable PC hardware.
Out-of-Scope: Silicon die micro-probing, PCB trace layer reconstruction, ASIC firmware reversing, or non-laptop peripherals.
  1. Confidence Threshold Gating: If a deduction path terminates with certainty $CF < 0.60$ (the calibrated threshold stored in boundary_rules.certainty_threshold), LapDoc refuses to assert a definitive diagnosis. It flags is_inconclusive = True and issues a limitation directive advising lab bench multimeter tests.
  2. Physical Damage Intercept: When conditions like conductive liquid ingress or burnt smell are detected, the system immediately short-circuits triage to prevent electrical fires.
  3. Domain Boundary Validator: The check_domain_boundary(symptom_text) method scans inputs for out-of-scope hardware (e.g., laser printers, mechanical hard drive platter repair) and refuses execution before false conclusions occur.

9. Why Symbolic AI Outperforms LLMs in Hardware Triage

Academic examiners frequently query why modern Deep Learning or Large Language Models (LLMs) were not used exclusively. LapDoc uses Symbolic AI for mission-critical reasons:

Explainability (XAI) Black-box neural weights. Cannot furnish formal mathematical proofs of its deductions. 100% Deterministic & Auditable. Every step maps directly to an explicit node ID and rule link.
Hallucination Risk High. Can invent false pinouts, fake voltage rails, and catastrophic repair advice. Zero Hallucination. Bounded strictly by curated, verified engineering facts in JSON.
Safety in Electronics Probabilistic output can recommend shorting live lithium-ion or high-voltage backlight rails. Safety-gated emergency stops (e.g., immediate battery disconnect protocols).
Compute & Field Portability Requires GPU clusters, high-speed Internet, and high API latency. Runs instantaneously on low-power CPUs from a bootable USB drive in offline field environments.
Formal Verifiability Non-deterministic; minor prompt changes alter diagnostic conclusions unpredictably. Unit tests formally verify graph acyclicity, score ranges, and rule coverage.

10. Academic Viva Defense Guide & Examination FAQ

Use these authoritative model answers during thesis presentations, viva defenses, or project examinations:

Q1: "Is an Expert System obsolete now that Large Language Models exist?"

Defense Answer: "No. In safety-critical diagnostic domains (such as electronics triage, aerospace fault monitoring, and clinical medicine), generative LLMs suffer from probabilistic hallucinations and lack verifiable causal reasoning. LapDoc implements Symbolic AI, which remains the gold standard when zero-hallucination guarantees, formal audit trails, and deterministic safety rules are mandatory. Furthermore, state-of-the-art AI architectures are increasingly neuro-symbolic, using symbolic engines like LapDoc as grounded verifiers for LLM interfaces."

Q2: "What proves your Knowledge Base is declarative and not procedural?"

Defense Answer: "Procedural code defines the flow of execution inside algorithms (if condition: do_action()). In LapDoc, knowledge_base.json contains pure declarative assertions of symptoms, relationships, costs, and certainty weights. The reasoning engine in engine.py contains zero laptop-specific rules. You could replace knowledge_base.json with an automotive transmission diagnostic schema, and engine.py would execute without altering a single line of Python code."

Q3: "How does LapDoc handle conflicting or uncertain information?"

Defense Answer: "LapDoc implements the Shortliffe-Buchanan Certainty Factor model. Each rule is assigned a certainty coefficient. When independent symptoms point to the same fault, we apply the MYCIN combination equation: $CF = CF_1 + CF_2(1 - CF_1)$. If conflicting evidence leaves the final certainty below our calibrated 60% decision threshold, the engine explicitly flags the result as inconclusive and advises physical multimeter/oscilloscope testing rather than making a speculative guess."

Q4: "Where is Working Memory located during execution?"

Defense Answer: "Working Memory is maintained dynamically through session history tuples. As the user confirms symptoms, the engine pushes assertions into the working memory fact base. The forward traversal algorithm evaluates candidate rules against this working memory to determine which questions to prune, which gateway to trigger, and when an early-exit intercept condition is met."

Q5: "How does the system ensure the diagnostic graph is valid?"

Defense Answer: "The test suite in tests/test_engine.py executes automated graph validation on every build. It verifies: (1) Graph acyclicity (no infinite recursion loops), (2) Referential integrity (every next_question pointer maps to an existing node), (3) Probability bounds ($0.0 \le CF \le 1.0$), and (4) Penalty score bounds across all 7 hardware categories."

11. Annotated Core Code Listings

1. Dynamic Inference Step & Leaf Resolution (engine.py)

def process_emergency_step(self, history: List[tuple[str, str]]) -> Dict[str, Any]:
    """
    Advances inference state using history sequence: [(node_id, option_key), ...]
    Derives terminal leaf or computes next candidate query.
    """
    if not history:
        return {"status": "in_progress", "current_node": self.get_node(self.emergency_entry), "trace": []}

    trace = []
    current_node_id = self.emergency_entry

    for i, (node_id, chosen_key) in enumerate(history):
        node = self.get_node(node_id)
        selected_option = next((opt for opt in node["options"] if opt["key"] == chosen_key), None)

        trace.append({
            "step": i + 1, "node_id": node_id, "title": node["title"],
            "chosen_label": selected_option["label"], "why": node["why"]
        })

        # Check for immediate leaf diagnosis (Short-Circuit Pruning)
        leaf = selected_option.get("leaf_diagnosis")
        if leaf:
            cf = leaf.get("certainty_factor", 1.0)
            is_inconclusive = cf < self.certainty_threshold
            return {
                "status": "concluded",
                "result": DiagnosticResult(
                    title=leaf["title"], issue=leaf["issue"],
                    remediation=leaf["remediation"], confidence_score=cf,
                    is_deterministic=leaf.get("is_deterministic", True),
                    is_inconclusive=is_inconclusive,
                    history_trace=trace
                ),
                "trace": trace
            }

        next_q = selected_option.get("next_question")
        if next_q:
            current_node_id = next_q

    return {"status": "in_progress", "current_node": self.get_node(current_node_id), "trace": trace}

2. Multi-Subsystem Health Scoring & Defect Aggregation (engine.py)

def evaluate_audit(self, answers: Dict[str, str]) -> AuditScorecard:
    """
    Evaluates observed symptoms across all 52 audit checks.
    Computes penalty deductions, category health ratings, and repair estimates.
    """
    category_penalties = {cat: 0 for cat in self.categories.keys()}
    flagged_defects = []
    cost_min_total, cost_max_total = 0, 0

    for nid, node in self.nodes.items():
        if nid == "q_emergency_triage":
            continue
        cat = node.get("category", "other")
        chosen_key = answers.get(nid)
        matched_opt = next((opt for opt in node["options"] if opt["key"] == chosen_key), node["options"][0])

        penalty = matched_opt.get("penalty", 0)
        category_penalties[cat] += penalty

        if not matched_opt.get("is_healthy", True) or penalty > 0:
            min_c, max_c = self._parse_cost_range(matched_opt.get("estimated_cost_usd", "$0"))
            cost_min_total += min_c
            cost_max_total += max_c
            flagged_defects.append({
                "node_id": nid, "title": node["title"], "observed": matched_opt["label"],
                "defect": matched_opt.get("defect_description", node["title"]),
                "penalty": penalty, "cost": matched_opt.get("estimated_cost_usd", "$0")
            })

    # Normalized score computation (0-100)
    total_penalty = sum(category_penalties.values())
    overall_score = max(0, min(100, 100 - int(total_penalty * 0.45)))
    grade, verdict = self._determine_grade_and_verdict(overall_score, flagged_defects)

    return AuditScorecard(
        total_score=overall_score, letter_grade=grade, verdict=verdict,
        category_scores={c: max(0, 100 - (p * 2)) for c, p in category_penalties.items()},
        flagged_defects=flagged_defects, total_estimated_repair_min=cost_min_total,
        total_estimated_repair_max=cost_max_total,
        summary_markdown=self._generate_audit_markdown(overall_score, grade, verdict, flagged_defects, cost_min_total, cost_max_total)
    )
